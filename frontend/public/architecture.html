ZK-STARK Password Hashing Architecture

Comprehensive guide to the authentication system, cryptographic proofs, and server-side efficiency.

System Overview

What Problem Does This Solve?

Traditional password authentication requires the server to:

  • Store hashes (bcrypt/argon2) — but databases can be breached
  • Compute memory-hard functions — expensive for login verification (5-100MB RAM per attempt)
  • Rate-limit login attempts — to prevent brute-force attacks

This system shifts the computational burden to the client (user's browser) while providing cryptographic proof that the computation was done correctly. The server never computes the expensive hash.

Key Insight: Instead of "send password → server hashes it", we use:

"client hashes password → proves it knows the hash → server verifies proof"

Why this approach is better:
  • Server never computes Argon2 (which costs 500ms + 1GB RAM)
  • Server only verifies proof (~200ms, no expensive hashing)
  • Proof verification is deterministic & non-interactive
  • Resistant to server-side timing attacks (computation is on client)
  • Attacker can't brute-force the server (client-side delay)

🚪 Login Failure Scenarios

  • Wrong password: Client hashes to different output → proof still valid but hash field doesn't match stored hash → 401 Unauthorized
  • Proof is forged: STARK verification fails at AIR/FRI check → 400 Bad Request
  • Hash field tampered: Our fix catches this — hash-nonce binding check fails → 400 Bad Request
  • User doesn't exist: Query returns null → 401 Unauthorized (no timing leak)

Authentication Workflows & Architectures

Overview: Three Authentication Patterns

This system supports multiple authentication workflows, each suited for different security and privacy requirements.

Pattern Server Stores Registration Hash Login Hash Best For
Verified Hash Storage H(password, salt) H(p, salt) H(H(p, salt), nonce) Standard authentication
ZK-Only (No Storage) Proof commitment only H(p, salt) H(H(p, salt), nonce) Maximum privacy
Salted Lookup salt (unique per user) H(p, salt) H(H(p, salt), nonce) Password breach mitigation

Pattern 1: Verified Hash Storage (Current Implementation)

This is the standard approach: server stores the hash, uses it to verify logins.

Registration: H(p, salt) → Store Hash

Registration Process: 1. User submits password p 2. Client: - Generate random salt s - Compute h₁ = H(p, s) ← First hash with salt - Generate STARK proof of h₁ 3. Server receives: {h₁, proof, username} 4. Server: - Verify STARK proof - Store h₁ in database Database stores: {username, h₁, algorithm, salt (if needed)}
Why this works:
  • Salt prevents rainbow table attacks
  • STARK proof verifies correct computation on client
  • Server never touches password or expensive hash computation
  • Can use strong memory-hard functions (Argon2id)

Login: H(H(p, salt), nonce) → Verify Against Stored

Login Process: 1. User submits password p 2. Server sends: {username, nonce} where nonce = random challenge 3. Client: - Look up stored salt for this username (or receive from server) - Compute h₁ = H(p, salt) ← Same as registration - Compute h₂ = H(h₁, nonce) ← Hash of hash with nonce - Generate STARK proof of h₂ 4. Server receives: {h₂, proof} 5. Server: - Verify STARK proof - Re-derive: expected_h₂ = H(stored_h₁, nonce) - Compare: if h₂ == expected_h₂ then LOGIN SUCCESS Login succeeds only if: ✓ STARK proof is valid (computation was correct) ✓ h₂ matches expected value (password was correct)
Double Hashing: Why H(H(p, s), nonce)?
  • Registration uses H(p, s): Expensive, memory-hard (Argon2id) Server stores this value, but client can't feasibly compute it per login attempt
  • Login uses H(H(p, s), nonce): Quick inner hash, then outer hash with nonce This is much faster but still cryptographically secure
  • Nonce prevents replay: Each login uses different nonce Same password → different proof each time
  • Proof binds both: STARK proof cryptographically verifies entire computation

Visual Flow

Registration: User: "password123" ↓ [Client: hash with Argon2] h₁ = Argon2("password123", salt) ↓ [Client: STARK proof] proof₁ = STARK_prove(h₁) ↓ [Send to server] Server stores: {user, h₁, salt} Login: User: "password123" Server sends: nonce=random123 ↓ [Client: re-derive h₁] h₁ = Argon2("password123", stored_salt) ↓ [Client: hash h₁ with nonce] h₂ = SHA256(h₁ || nonce) ↓ [Client: STARK proof of h₂] proof₂ = STARK_prove(h₂) ↓ [Send {h₂, proof₂}] Server: - Verify proof₂ - Compute: expected = SHA256(stored_h₁ || nonce) - If h₂ == expected: LOGIN SUCCESS

Pattern 2: ZK-Only (No Hash Storage)

For maximum privacy, server never stores the actual hash. Instead, it stores a commitment to the hash and verifies only through zero-knowledge proofs.

The Challenge: Can We Authenticate Without Storing H(p)?

Answer: Yes, using commitments!

Instead of storing h₁ = H(p, s), store a cryptographic commitment:
commitment = Poseidon(h₁, pepper)
where pepper is server-secret (never given to client).

Registration: H(p, salt) → Store Commitment Only

Registration Process: 1. Client: h₁ = Argon2(p, salt) 2. Client: Generate STARK proof of h₁ 3. Client sends: {h₁, proof} ← hash visible during registration 4. Server receives: - Verify STARK proof - Compute: C = Poseidon(h₁, secret_pepper) - Store ONLY C in database (forget h₁) - h₁ is never stored, only commitment Database stores: {username, C, algorithm} where C = Poseidon(h₁, pepper) and pepper is server-secret

Login: Prove Knowledge of H(H(p, salt), nonce) Without Revealing

Login Process: 1. Server sends: {nonce, pepper_share} where pepper_share = pepper ⊕ session_key 2. Client: - Compute h₁ = Argon2(p, salt) [same as registration] - Compute pepper = pepper_share ⊕ session_key - Verify: C_expected = Poseidon(h₁, pepper) - Compute h₂ = SHA256(h₁ || nonce) - Generate STARK proof that: ✓ h₁ commits to correct password ✓ h₂ = SHA256(h₁, nonce) ✓ C_computed matches stored C 3. Server: - Verify STARK proof - Does NOT see h₁ or h₂ (only proof) - Knows client proved knowledge of correct password Login succeeds purely through ZK proof verification!
Advantages of ZK-Only:
  • No breach of H(p): Server never stores the hash itself Even if database is stolen, attacker gets only commitments
  • Perfect forward secrecy: Old proofs are useless Each login generates new proof with new nonce
  • Reduced server liability: Can't leak what's not stored
  • Privacy-first: Alignment with privacy regulations (GDPR, etc.)

Implementation Notes

Server-side: pepper = 256-bit secret, stored in secure key management Registration: C = Poseidon(h₁, pepper) DELETE h₁ after verification (don't store) Login: pepper_share = pepper ⊕ session_key Send pepper_share over HTTPS Client recovers pepper using session_key Client proves it knows h₁ via proof Server never sees h₁ Problem to solve: How does client prove knowledge of h₁ without revealing it? Answer: STARK proof that proves the computation! The proof itself becomes the authentication credential.

Pattern 3: Salted Lookup (Hybrid)

A middle ground: server stores salt (cheap) and uses it to verify, but not the hash itself.

Registration: Generate & Store Salt

Registration Process: 1. Client: - h₁ = Argon2(p, salt) - proof = STARK_prove(h₁) 2. Server: - Verify proof - Store: {username, salt, proof_hash} - Do NOT store h₁ (salt is enough) Database stores: {username, salt, algorithm} Salt allows server to validate password without storing hash.

Login: Derive Expected Hash From Stored Salt

Login Process (Server-Side): 1. User claims identity: username 2. Server looks up: stored_salt 3. Server sends: {nonce, salt} ← Server reveals salt 4. Client: - h₁ = Argon2(password, salt) ← Derives h₁ from password + salt - h₂ = SHA256(h₁, nonce) - proof = STARK_prove(h₂) 5. Server: - Verify STARK proof - Verify structure: proof proves knowledge of some h₁ - Accept login (no need to compare against stored value!) Key insight: Server doesn't verify "is this the right hash?" Instead: "Can you prove you know SOME h₁ that led to this proof?" With cryptographic proof, this IS enough!
Advantages of Salted Lookup:
  • Salt stored separately: Different users have different salts Rainbow table attacks impossible (each user has unique salt)
  • No hash storage: Doesn't store H(p, s), only the salt s
  • Simpler than ZK-only: No need for pepper, commitments, or complex proofs
  • Good privacy/usability balance: Practical and secure

Workflow Decision Tree

Choose your authentication pattern based on your requirements:

Question 1: Must you store the password hash?
  • Yes, for compliance/auditability: Use Pattern 1 (Hash Storage)
    Most enterprises, banking, healthcare need hash storage for verification
  • No, prioritize privacy: Continue to Question 2
Question 2: Can your server manage secret peppers?
  • Yes, HSM/secure enclave available: Use Pattern 2 (ZK-Only)
    Maximum privacy, no hash storage, commitment-based
  • No, keep it simple: Use Pattern 3 (Salted Lookup)
    Salt is simple, no complex secrets, still privacy-preserving

Technical Implementation Guide

Pattern 1: Hash Storage (Standard)

Client code: password = "userInput" salt = cryptographically_secure_random(32) h1 = argon2id(password, salt, {time: 2, mem: 65536, ...}) proof = starkProver.generateAuthProof(h1, salt) // On login: nonce = "server_challenge_random" h2 = sha256(h1 + nonce) proof2 = starkProver.generateAuthProof(h2, nonce) Server code: // Registration verifySTARK(proof) // Verify h1 computation db.store({username, hash: h1, algorithm: "argon2id"}) // Login verifySTARK(proof2) // Verify h2 computation expected_h2 = sha256(db.hash + nonce) if (h2 == expected_h2) → LOGIN_SUCCESS

Pattern 2: ZK-Only (Advanced)

Server code: pepper = cryptographically_secure_random(256) // Secret! // Never expose pepper directly Registration: commitment = poseidon(h1_from_client, pepper) db.store({username, commitment: commitment}) // h1 is forgotten Login: pepper_share = pepper XOR session_key send_to_client(pepper_share) // Client recovers pepper = pepper_share XOR session_key // Client proves it knows h1 via STARK // Server never sees h1, only verifies proof

Pattern 3: Salted Lookup (Simple Privacy)

Client code: password = "userInput" salt = server_provided_salt h1 = argon2id(password, salt) nonce = server_challenge h2 = sha256(h1 + nonce) proof = starkProver.generateAuthProof(h2, nonce) Server code: // Registration db.store({username, salt: random_salt}) // Login salt = db.lookup_salt(username) send(salt, nonce) // Client can now compute h1, prove h2 verifySTARK(proof) // No comparison needed! // Proof itself is sufficient authentication

Security Implications of Each Pattern

Pattern 1: If Server Database is Breached

  • Attacker has: {username, h₁ = Argon2(p, s), s if stored}
  • Attacker's goal: Reverse h₁ to get p
  • Attack cost: Argon2(t=2, m=65536) ≈ 500ms per guess For 1000 guesses: ~500 seconds = 8 minutes
  • Mitigation: Use strong parameters, rate-limit guesses

Pattern 2: If Server Database is Breached

  • Attacker has: {username, C = Poseidon(h₁, pepper)}
  • Attacker's goal: Break Poseidon(h₁, pepper) where pepper is unknown
  • Attack cost: Collision attack on Poseidon ≈ 2^128 work (practically impossible)
  • Result: Breach is almost inconsequential Attacker has commitment but can't authenticate

Pattern 3: If Server Database is Breached

  • Attacker has: {username, s (salt), algorithm}
  • Attacker's goal: Generate valid STARK proof
  • Attack cost: Must know password p to compute h₁ Then: Argon2(p, s) ≈ 500ms per guess
  • Result: Similar to Pattern 1 (if salt is leaked) But uniqueness per user helps

Mathematical Foundation

STARK: Scalable Transparent Argument of Knowledge

A STARK is a zero-knowledge proof that proves a computation was performed correctly without revealing the secrets involved. Our system uses STARK to prove:

"I computed hash(password) and received this output, without sending you the password"

Computation Being Proven: MiMC-7 Hash

The STARK proof embeds a complete execution trace of MiMC-7 (Minimal Multiplicative Complexity):

MiMC-7(input): x₀ = input for i = 0 to 127: xᵢ₊₁ = (xᵢ + Cᵢ)^7 mod p return x₁₂₈ where: p = 21888242871839275222246405745257275088548364400416034343698204186575808495617 Cᵢ = canonical round constants (256-bit field elements) ^7 = Frobenius exponent (highly nonlinear)

Why MiMC-7? It's optimized for zero-knowledge proofs — requires only ~128 multiplications, vs. SHA-256 which would require millions of bit operations.

STARK Protocol Structure

Phase 1: Commitment ┌─ Trace Commitment (trace_root) │ Prover commits to execution trace: [x₀, x₁, x₂, ..., x₁₂₈, padding...] │ Using Merkle tree over low-degree extension │ ├─ Quotient Commitment (q_root) │ Encodes the AIR constraints: P(wz) = (P(z) + C)^7 │ Quotient: Q(z) = ConstraintError(z) / Vanishing(z) │ └─ FRI Commitment (8 fri_roots) Merkle roots of FRI proof layers Phase 2: Challenge ┌─ Fiat-Shamir: Derive random challenges from commitments │ friAlpha = H(nonce, trace_root, q_root, ...) │ friAlphas[i] = H(...previous challenges, fri_roots[i-1]) │ └─ Query indices: idx₁, idx₂, ..., idx₅₀ From friAlphas, extract 50 random evaluation points Phase 3: Response ┌─ Query openings at 50 points: │ - trace values: P(z), P(wz) │ - quotient value: Q(z) │ - Merkle paths to prove inclusion │ ├─ FRI proof: 8-fold folding down to constant │ For each layer: show values + sibling + Merkle paths │ └─ Boundary proof: trace[128] = hash_output With Merkle path Phase 4: Verification ┌─ Check AIR constraints at all 50 points │ P(wz) = (P(z) + C)^7 + Q(z) * Z_vanishing(z) │ ├─ Check FRI consistency: folding protocol │ Each layer: even + alpha * odd = next_folded_value │ ├─ Check boundary: hash_output ∈ committed trace │ └─ Check rc_commitment: canonical round constants used

Proof Binding Mechanism

For bcrypt/argon2 proofs, the hash output is cryptographically bound to the STARK proof:

Prover side: nonce = padded_hex_encoding(bcrypt_hash_output) Transcript.absorb(nonce) ← First thing absorbed [proceed with STARK proof generation...] friAlpha = Transcript.challenge() ← Depends on nonce Verifier side: 1. Extract hash from public_inputs.hash 2. Recompute: expected_nonce = padded_hex(hash) 3. Check: public_inputs.nonce == expected_nonce ↳ If no match, REJECT (hash was tampered) 4. If match, use nonce to derive friAlpha 5. Verify FRI proof with correct friAlpha
Why this binding is critical: Without it, an attacker could:
  • Generate proof for password "MyPassword" → hash = H1
  • Change proof.hash to H2 (a different password's hash)
  • Send to server → server accepts it (BEFORE the fix)
Now the hash-nonce check detects this tampering immediately.

FRI (Fast Reed-Solomon Interactive Oracle Proofs)

FRI proves a polynomial has bounded degree using iterative folding:

Goal: Prove deg(H) ≤ 256 where H = P(x) + friAlpha * Q(x) Layer 0 (2048 points): H₀(x) → commit to M₀ (Merkle tree) Challenge: friAlpha₀ Fold: H₁(y) = (H₀(√y) + H₀(-√y))/2 + friAlpha₀ * (...)/(2√y) Layer 1 (1024 points): H₁(y) → commit to M₁ Challenge: friAlpha₁ Fold: H₂(z) = ... ... repeat 8 times ... Final (8 points): H₈ = constant polynomial c Verify: current_value == c Soundness: If H doesn't have bounded degree, folding cannot produce the correct constant. Probability attacker fools verifier ≈ (256/2048)^50 = 2^-150

  • Attacker Goal: Log in as a user without knowing the password

  • Attack Surface 3: Guess password by trying many hashes (hard due to client-side cost)

Post-Quantum Considerations

STARKs are quantum-resistant (unlike SNARK curves which use discrete log). The security comes from:

  • AIR constraints: Low-degree polynomial evaluation (no quantum speedup)
  • FRI folding: Polynomial commitment via Merkle trees (hash-based, quantum-safe)
  • Merkle trees: Built on Poseidon (sponge construction, no known quantum vulnerabilities)

Even if quantum computers arrive, this system remains secure (unlike RSA, ECDSA, pairing-based SNARKs).

Server-Side Storage & Validation

Database Schema

What's NOT stored:
  • ❌ Password (never transmitted)
  • ❌ Full STARK proof (too large, verified once and discarded)
  • ❌ Private/secret information

What IS stored:
  • ✅ Hash (proves proof was about correct computation)
  • ✅ Proof hash (audit trail, replay detection)
  • ✅ Algorithm metadata (reproducibility)
  • ✅ Verification timestamps (security events)

Verification Process on Server

Input: {hash, proof} Step 1: Hash-Nonce Binding Check (NEW FIX) expected_nonce = padded_hex(hash) if proof.public_inputs.nonce != expected_nonce: return 400 Bad Request Step 2: STARK Proof Verification result = verifier.verify(proof) if !result.success: return 400 Bad Request Checks: ✓ Nonce consistency ✓ Round-constant commitment ✓ Boundary constraint (hash ∈ trace) ✓ AIR constraints (50 points) ✓ FRI folding (8 layers) ✓ Merkle path integrity ✓ No tampering detected Step 3: Hash Storage & Lookup stored_hash = db.users.find_by_username(username).hash if hash == stored_hash: return 200 OK (login success) else: return 401 Unauthorized (wrong password) Step 4: Audit Log log_event({ user_id, action: 'login', proof_verified: true, hash_matched: (hash == stored_hash), timestamp: now })

Replay Attack Prevention

Can an attacker capture a valid login proof and replay it?

Answer: No (with proper session management)
  • The proof is tied to the hash of the password, not the password itself.
  • The hash is deterministic — same password → same hash.
  • A captured proof can be replayed to log in as that user (from any network).
  • Solution: Use nonce binding or one-time proofs:
    • Include server-generated nonce in proof: proof_nonce = H(server_random || timestamp)
    • Or: Include timestamp in STARK nonce, reject proofs older than 60 seconds
    • Or: Use typical session tokens after proof succeeds (user logs in once, session persists)

Database Breach Scenario

What if the hash database is stolen?

  • Attack: Attacker has {username: "alice", hash: bcrypt_output}
  • Goal: Generate a valid proof for alice's account
  • Problem: Generating a proof requires knowing the password (or brute-forcing it). The attacker has the hash but not the password.
  • Cost: Argon2(mem=1GB, time=1) takes ~500ms to compute once (attacker has to compute it once they guess the password to get the proof). This is expensive for large-scale attacks.
  • Conclusion: Breach is bad but not catastrophic. The hash is still useful for password checking (with Argon2 cost), but doesn't allow instant account takeover.

Why Shifting to Client-Side Matters

Traditional approach bottleneck:

All 1 million users logging in during peak hour must hit the server. Server must compute Argon2 1M times = 500,000 seconds of CPU work. With 32-core server: 500,000 / 32 = 15,625 seconds = 4.3 hours of compute.

Each user waiting for: Network(50ms) + Arg2(500ms) + DB(10ms) = ~560ms
STARK-based approach:

Each user computes Argon2 on their own machine (parallelize across cores/devices). Server only verifies proofs (~200ms per proof, easily parallelizable). Server needs: 32 cores * (3600 seconds) / 200ms = 576,000 proofs per hour = 160 proofs per second.

Each user waiting for: Network(50ms) + STARK verify(200ms) + DB(10ms) = ~260ms
Result: 2.15x faster login, massive server CPU savings

Multi-Device & Offline Scenarios

  • Desktop login: User's machine computes proof (leverage CPU cores). High-spec device = faster proof generation.
  • Mobile login: User's phone computes proof (uses device resources). May be slower (~3-4 seconds on mobile), but still acceptable.
  • Smart TV / IoT: Can't compute Argon2 efficiently? Fall back to simpler MiMC-7 STARK (2 seconds, constant output).
  • Offline generation: User can generate proof without internet, submit later when online (no real-time requirement).

Rate Limiting & DoS Protection

The server-side benefit is subtle but important:

  • Traditional: Rate limit by IP (e.g., 10 login attempts per minute). Attacker can still hit server 10 times with full Argon2 cost. Server CPU: 5 seconds of compute per minute per attacker.
  • STARK-based: Rate limit by IP (e.g., 10 attempts per minute). Server only verifies proofs, not computing. Server CPU: 2 seconds of compute per minute per attacker (10x less).
    Plus: Proof generation on client is expensive → natural DoS protection.
