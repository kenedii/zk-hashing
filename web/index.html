Research prototype · unaudited

Proving password hashes inside a STARK

zk-hashing executes complete Argon2id, bcrypt and MiMC-7 computations inside the Miden virtual machine and proves them with hash-based STARKs. The goal is a login in which the client proves it knows a password that matches a stored commitment, without sending the password or any value derived from it. This page reports what has been built, what it costs to prove, and where the approach currently stops.

Summary of findings

  • Complete circuits. RFC 9106 Argon2id v1.3 and bcrypt 2b run in full as Miden programs and agree with the RustCrypto reference implementations, including a 64-case Argon2id parameter matrix.
  • Proof generation is memory-bound. The generic prover holds the entire padded execution trace in memory. The smallest Argon2id setting needs a 225-row trace. Its largest single allocation is 102 GiB, and the estimated peak is about 270 GiB. bcrypt at cost 4 needs 229 rows, an estimated 4 TiB.
  • Verification is cheap. A 172 KB MiMC-7 proof verifies in milliseconds with the WebAssembly build of the verifier, in any modern browser.
  • Browser proving stops at the 32-bit WebAssembly limit. Proving even the small MiMC-7 circuit peaks at 4.25 GiB natively. In Chromium, the wasm32 build climbs to the 4 GiB address-space ceiling and stops making progress. A 64-bit (Memory64) build is the direct fix.
  • Hash-only assumptions. Proof soundness rests on collision-resistant hash functions rather than elliptic-curve assumptions, so it is not exposed to Shor's algorithm. Practical deployment is limited by proving cost, not by this property.

Protocol

Two messages per login. The password is private input to the proof and is never transmitted.

  1. Client

    Register

    Choose a random 16-byte salt, compute the password hash, and send a Poseidon2 commitment to the output together with the salt and hash parameters. The server stores these three values.

  2. Server

    Challenge

    At login, issue a fresh, single-use 128-bit challenge.

  3. Client

    Prove

    Run the complete hash in the Miden VM with the password as private input and produce a STARK showing that the program accepted, i.e. that the computed hash matches the stored commitment. The challenge is a public input, which binds the proof to this login.

  4. Server

    Verify

    Verify the proof against the stored commitment, the issued challenge, the expected parameters and the hash of the exact compiled program, then mark the challenge as spent. All public values come from the server's records, never from the proof envelope.

Why proving cost dominates

Password hashes are expensive by design, and a general-purpose zkVM prover pays that cost again for every recorded step.

The prover materializes the full execution trace and its low-degree extension before committing, and the trace length is padded to the next power of two. Lowering the proof security level does not help, because the trace itself is the dominant cost. Memory therefore scales with the hash's work factor: the property that makes Argon2id and bcrypt resist guessing is exactly what makes them expensive to prove.

Security analysis

What a proof establishes, how the design compares with OPAQUE, and what changes against a quantum adversary.

What an accepted proof establishes

For a pinned program hash, stored commitment, salt, parameters and one-time challenge, an accepted proof shows that the program executed to completion on some private password and returned success. Every byte of the password and salt is range-checked in the circuit, domain tags prevent cross-algorithm and concatenation ambiguity, and the verifier rejects any proof whose public values differ from the server's records.

Post-quantum considerations

OPAQUE's oblivious PRF and key exchange are built on elliptic-curve groups. A quantum attacker able to run Shor's algorithm and observe a login could recover the server's OPRF key and then test password guesses offline, which removes OPAQUE's central guarantee; the IETF hybrid PQ-PAKE draft notes that OPAQUE is exposed to harvest-now-decrypt-later attacks. Post-quantum aPAKE constructions, including the hybrid CPaceOQUAKE+ proposal and KEM-based compilers, are under active development but not yet standardized.

A STARK uses only hash functions and Fiat–Shamir, and the underlying succinct-argument construction has a security proof in the quantum random-oracle model. Proof forgery therefore has no known Shor-style shortcut. Two qualifications apply. First, quantum search reduces the effective security margin, and Miden's default 96-bit conjectured level is modest; a higher level would be appropriate for a post-quantum claim. Second, the protocol provides no session key or server authentication, so a post-quantum deployment also needs post-quantum TLS (for example the hybrid ML-KEM key exchange now used by default in major browsers). The interactive baseline on this page uses secp256k1 and is not post-quantum.

Limitations

  • Proving cost. Argon2id and bcrypt proofs at realistic parameters are orders of magnitude beyond client hardware with a general-purpose prover. The demonstrated settings (8 KiB Argon2id, bcrypt cost 4) are far below recommended password-storage parameters.
  • Not zero-knowledge. Miden VM proofs in this configuration do not add hiding randomness; Miden's roadmap lists perfect zero-knowledge as future work. Proofs should be treated as proofs of correct computation and handled as credential material.
  • Commitment exposure. The commitment is a public input, so a recorded login or a database leak permits offline guessing at the cost of one hash evaluation per guess. MiMC-7 provides no meaningful resistance to guessing.
  • No key agreement. The protocol authenticates the client to the server but does not establish a session key or authenticate the server; it depends on TLS.
  • Side channels. Argon2id uses data-dependent addressing, and VM execution is not constant-time. Timing and resource side channels have not been analysed.
  • Scope. Passwords are limited to 1–64 bytes, salts to 16 bytes and Argon2id lanes to 1–4; the Argon2id secret and associated-data inputs are not supported.
  • Assurance. Miden VM and the Rust-to-Miden compiler are experimental. This code has not been independently audited and must not protect real accounts. For password login without transmitting passwords today, use OPAQUE (RFC 9807).

    B. MiMC-7 proving in the browser (wasm32)

    The same runtime, compiled to 32-bit WebAssembly, was asked to prove MiMC-7 in headless Chromium (Playwright build 1194), with renderer memory sampled every 10 s. Raw data (CSV).

    Finding. Memory rose to about 3.65 GiB within two minutes, reached 4.03 GiB at four minutes, then stayed flat. After that the page thread was idle, and no proof or error appeared after 14.5 minutes. This reproduces the earlier result on Windows Chromium. The prover's native peak is above what a 32-bit WebAssembly address space can hold, so in-browser proving needs a Memory64 build.

    Finding. The prover committed 218 GiB, 1.7× physical RAM. The committed memory fit within the page file, so the allocation itself succeeded, but the prover could not run efficiently from a hard drive. After the first four minutes it was waiting on disk almost all the time. The system was so busy paging that the monitoring script recorded no samples for 55 minutes (shaded in the charts). It used 31.6 minutes of CPU time in 7 hours, and in the last two hours it used 0.3% of a core. No proof was produced before the log ended at 7.0 hours. The run also used the single-threaded prover, so even with enough RAM it would have used only one core.

    Conclusions

    1. Verification works everywhere it was tried. Three independently generated MiMC-7 proofs verify natively and in the browser, taking 10–100 ms each in the browser. A tampered proof is rejected by both verifiers.
    2. The memory requirement is about 2.6× higher than earlier estimates. The measured peak of about 8.5 KB per trace row puts the smallest Argon2id proof at roughly 220–270 GiB, consistent with the 218 GiB committed in run C. bcrypt at cost 4 is roughly 4 TiB.
    3. Browser proving is blocked by the 32-bit address space, not by speed. Even MiMC-7 sits just above the 4 GiB wasm32 limit. A Memory64 build is the direct next step.
    4. A disk-backed page file does not substitute for RAM. The proving workload's memory access pattern turns paging into a near-total stall. A full Argon2id proof needs a machine with roughly 256–512 GiB of RAM, run with the multi-threaded prover. Alternatively, it needs a prover that streams the trace or splits the computation into segments.

    Future work

    • Segmented proving

      bcrypt and small-memory Argon2id carry little state between rounds (1,042 words and 8 KiB respectively). Splitting execution into segments linked by blinded state commitments would let each segment be proved independently, in parallel or on separate machines, at roughly 13 GiB per 222-row segment. Blinding is required so that intermediate commitments do not allow cheaper guessing.

      Designed

    • Zero-knowledge and higher security levels

      Adopt hiding (perfect zero-knowledge) proofs when the Miden prover supports them, and raise the conjectured security level above 96 bits for a post-quantum argument.

      Depends on Miden

    • Memory64 browser proving

      MiMC-7 needs 4.25 GiB, just above the wasm32 ceiling. A wasm64 build (Chrome 133+, Firefox 134+) raises the limit to 16 GiB and should allow the first in-browser proof. Other Memory64 workloads run 10–100% slower. Web Workers could recover some of that through parallelism.

      Next step

    • A prover specialised for password hashes

      A purpose-built constraint system for Blake2b/BlaMka or Blowfish, or a streaming prover that keeps the trace out of core, could reduce memory by orders of magnitude. This is the main open problem between the prototype and a practical login.

      Open problem
