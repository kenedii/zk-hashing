How a login works

Two messages per login, and the only secret never leaves the browser.

  1. In the browser

    Register

    Pick a random salt, hash the password, and send a commitment to the result along with the salt and hash settings. The server stores those three things.

  2. On the server

    Send a challenge

    At login, send a fresh, single-use 128-bit challenge.

  3. In the browser

    Prove

    Run the full hash inside the Miden VM with the password as private input, and produce a STARK proof that the result matches the stored commitment. The proof is tied to this challenge.

  4. On the server

    Verify

    Check the proof against the stored commitment, the challenge it issued and the exact compiled program. Then mark the challenge used, so the same proof can't log in twice.

Where it stands

All three hashes run end to end inside the circuit. One can be proved today on ordinary hardware.

Algorithm What the circuit computes VM cycles Trace rows Proof
Argon2id v1.3 RFC 9106 in full: Blake2b, H′, 1 KiB blocks, BlaMka, hybrid addressing, passes, slices and lanes. Matches RustCrypto across 64 parameter cases. 19,593,971 225 Needs ~102 GiB
bcrypt 2b The full EksBlowfish key schedule, 2cost key and salt expansions, and 64 encryptions of the magic string. The 1,042 table words are checked against an in-circuit commitment. 367,224,034 229 Needs ~1.6 TiB
MiMC-7 Poseidon2 absorbs the password and salt, then all 220 MiMC rounds run. Cheap to prove, but not memory-hard, so it's a stand-in for testing the protocol rather than for storing passwords. 430,204 219 Proved in 39 s, 172 KB

What's blocking Argon2id and bcrypt

Prover memory. Password hashes are slow on purpose, and a general-purpose prover pays that cost again for every step it records.

The prover writes out the whole execution trace and its low-degree extension before it commits to anything, and the row count rounds up to the next power of two. A browser tab can address at most 4 GiB, and even MiMC stalled at that limit in Chromium. For now, proofs come from a native prover and the browser verifies them. Turning the proof-security dial down doesn't help, because the trace itself is what's too big.

    What's next

    • Publish a real Argon2id proof

      Run the Argon2id prover once on a cloud machine with 256 GiB or more and publish the proof. Anyone can then verify it on this page in milliseconds, even on a phone. bcrypt at cost 4 needs roughly 2 TiB.

      Planned

    • Prove one round live in the browser

      Small circuits for a single Blowfish encryption or one Blake2b compression should fit under the browser's limit, showing the building blocks of bcrypt and Argon2id being proved in front of the visitor.

      Needs measuring

    • A prover built for password hashes

      A purpose-built constraint system, or a prover that streams its trace to disk, could cut memory by orders of magnitude. That's the open problem between this project and a practical login.

      Open problem

    Current limits

    • This is research code. The Miden VM is alpha software, and none of this has had an independent audit.
    • Proofs use Miden's 96-bit security level.
    • It hasn't been confirmed that the proofs hide every detail of the password, so treat them as proofs of correct computation rather than proven zero-knowledge.
    • If the server's database leaks, the stored commitments can be attacked offline, like any password hash. MiMC is fast to guess against, so only Argon2id and bcrypt are meant for real use.
    • Systems that need password login without sending passwords today should use OPAQUE (RFC 9807).
