1. Notation

All arithmetic in the proof system takes place in the Goldilocks prime field

p=264−232+1,𝔽p=ℤ/pℤ.

Since p−1=232⋅3⋅5⋅17⋅257⋅65537, the multiplicative group 𝔽p× contains a cyclic subgroup of every order 2k with k≤32. This is what makes fast power-of-two evaluation domains available.

  • w∈{0,1}8ℓ, 1≤ℓ≤64: the password (the witness).
  • s∈{0,1}128: a per-user random salt.
  • θ: the hash parameters, for example θ=(m,t,planes) for Argon2id.
  • Hθ(w,s): the password hash (Argon2id, bcrypt or MiMC-7) with output y.
  • 𝖯𝟤: a sponge built on the Poseidon2 permutation over 𝔽p, with output in 𝔽p4.
  • P: the compiled Miden program that evaluates the statement; hP∈𝔽p4 is its program hash.
  • n∈{0,1}128: a single-use challenge (nonce) issued by the server.
  • a←RS: a is sampled uniformly at random from the set S.

2. Registration and commitment

At registration the client samples s←R{0,1}128, computes y=Hθ(w,s) and sends the commitment

C=𝖯𝟤(τalg ∥ y1,…,y∣y∣ ∥ s1,…,s16 ∥ θ)∈𝔽p4

together with s and θ. Here τalg is a domain-separation tag for the algorithm, and every output byte yi and salt byte si occupies its own field element. Encoding each byte separately, with explicit lengths and tags, makes the encoding injective, so two different tuples (y,s,θ) cannot collide through ambiguous packing.

The server stores (C,s,θ). C is binding: finding a second password with the same commitment requires either a collision in 𝖯𝟤 or a second preimage of Hθ. C is not hiding: it is a deterministic function of w, so anyone holding C can test a candidate w′ by recomputing it. This is the same exposure as a conventional password-hash table, and the cost of each guess is dominated by evaluating Hθ.

3. The proved relation and the login protocol

For a fixed program P, the proof system proves membership in the NP relation

ℛP={(x,w)  :    x=(C,s,θ,n),    1≤∣w∣≤64,𝖯𝟤(τalg ∥ Hθ(w,s) ∥ s ∥ θ)=C}.

The challenge n plays no role in the predicate itself. It is a public input of the program, and public inputs are absorbed into the Fiat–Shamir transcript (Section 6). A proof generated for n therefore does not verify for any n′≠n, which is what binds the proof to a single login attempt.

A login then consists of two messages:

  1. The server samples n←R{0,1}128 and sends it to the client.
  2. The client computes π←𝖯𝗋𝗈𝗏𝖾(P,x,w) with x=(C,s,θ,n) and sends π.

The server accepts if and only if

𝖵𝖾𝗋𝗂𝖿𝗒(hP,x,π)=1andn∉𝒩spent,

after which it sets 𝒩spent←𝒩spent∪{n}. The verifier takes C, s, θ and n from its own records, never from the proof envelope, and pins hP, so a client cannot substitute a cheaper program. With q challenges issued over the lifetime of the system, the probability that any two coincide is at most q2/2129.

4. Required properties

Let (𝖯𝗋𝗈𝗏𝖾,𝖵𝖾𝗋𝗂𝖿𝗒) be a non-interactive argument for ℛP. Three properties matter for authentication.

Completeness
An honest client is always accepted: Pr⁡[𝖵𝖾𝗋𝗂𝖿𝗒(hP,x,𝖯𝗋𝗈𝗏𝖾(P,x,w))=1]=1 for all (x,w)∈ℛP.
Knowledge soundness
For every efficient prover 𝒫∗ there is an efficient extractor ℰ, with oracle access to 𝒫∗, such that
Pr⁡[𝖵𝖾𝗋𝗂𝖿𝗒(hP,x,π∗)=1  ∧  (x,ℰ𝒫∗(x))∉ℛP]≤κ,
where κ is the knowledge error. An accepted proof thus implies knowledge of a valid password, not merely the existence of one.
Zero knowledge
There is an efficient simulator 𝒮 that, given only x, produces proofs indistinguishable from real ones: {𝖯𝗋𝗈𝗏𝖾(P,x,w)}≈{𝒮(x)} for all (x,w)∈ℛP.

The current implementation provides completeness and, under the usual conjectures, knowledge soundness at the 96-bit level. It does not provide zero knowledge. The prover does not randomize the execution trace, so the committed polynomials are deterministic functions of w. The consequences are discussed in the Security analysis.

5. Arithmetization

Running P on (x,w) for L cycles produces an execution trace, a matrix whose rows are successive machine states:

T∈𝔽pN×k,N=2⌈log⁡2L⌉.

Let ω generate the subgroup ℋ=⟨ω⟩ of order N. Each column j is interpolated to a polynomial tj∈𝔽p[X] with deg⁡tj<N and tj(ωi)=Ti,j. The VM's semantics are expressed as an algebraic intermediate representation (AIR): a set of low-degree polynomials fℓ such that consecutive rows are valid exactly when

fℓ(t(X), t(ωX))=0for all X∈ℋ∖{ωN−1},

together with boundary constraints that fix the public inputs x and the output [1] in the first and last rows. A polynomial vanishes on a set exactly when it is divisible by that set's vanishing polynomial. Since Zℋ(X)=∏h∈ℋ(X−h)=XN−1, the constraints hold if and only if each

qℓ(X)=fℓ(t(X),t(ωX)) (X−ωN−1)XN−1

is a polynomial, of degree below (dℓ−1)N+1 where dℓ=deg⁡fℓ. The verifier draws random weights αℓ and works with the single composition polynomial q(X)=∑ℓαℓ qℓ(X).

The prover evaluates every tj and q on a larger coset 𝒟=g⟨μ⟩ with ∣𝒟∣=βN; this is the low-degree extension, with blowup factor β. It then commits to the evaluations with Merkle trees. Holding T, its extension and the trees in memory is what makes prover memory grow linearly in N (Section 9).

Password hashes are expensive to arithmetize because they are built from 64-bit word operations. Argon2id's BlaMka mixing step, for example, computes

a←a+b+2⋅lo32(a)⋅lo32(b) mod 264.

Wrap-around modulo 264 is not native to 𝔽p, so each 64-bit word is represented by two 32-bit limbs with range checks, and every addition, rotation and XOR expands into several VM cycles.

6. Low-degree testing and Fiat–Shamir

The verifier samples an out-of-domain point z∉𝒟. The prover reveals t(z), t(ωz) and q(z), and the verifier checks the constraint identity at z. What remains is to show that the committed evaluations really come from polynomials of the claimed degree. Equivalently, the prover must show that quotients such as

tj(X)−tj(z)X−z

are low-degree. This is done with FRI (Fast Reed–Solomon Interactive Oracle Proof of Proximity). In each round, a function f(i) on a domain 𝒟i is folded with a random γi:

f(i+1)(X2)=f(i)(X)+f(i)(−X)2+γi f(i)(X)−f(i)(−X)2X.

Each fold halves both the degree bound and the domain. After about log⁡2N rounds the remaining function is a constant, sent in the clear. The verifier then checks fold consistency at q randomly chosen positions, using Merkle authentication paths.

The protocol above is interactive. The Fiat–Shamir transformation makes it non-interactive by replacing each verifier challenge with a hash of the transcript so far:

ρi=ℋ(x ∥ root1 ∥ ⋯ ∥ rooti).

Because the public input x (and so n) enters the very first hash, every challenge, and therefore the whole proof, depends on it. Since ∣𝔽p∣≈264 is too small for the required error bounds, random challenges are drawn from an extension field of 𝔽p.

7. Soundness and proof size

Under the standard conjecture on the proximity gap of Reed–Solomon codes, each FRI query catches a prover whose committed function is far from low-degree with probability about 1−1/β. A grinding (proof-of-work) condition of g bits further raises the cost of searching for favourable Fiat–Shamir challenges. The conjectured security level is then approximately

λ≈min⁡{ qlog⁡2β+g,    λℋ },

where λℋ is the collision resistance of the hash used for commitments. For example, q=27 queries with β=8 and g=16 give 27⋅3+16=97 bits; the proofs here are generated at Miden's 96-bit level. Proof size and verification time are polylogarithmic in the computation length: O(qlog⁡2N) hash digests and field elements. This is why a 219-row execution yields a 172 KB proof that verifies in milliseconds.

8. The three hash functions

Argon2id (RFC 9106)

A memory-hard function. It fills m blocks of 1 KiB, in t passes over planes lanes. Each block is computed by a compression function built from BlaMka-modified Blake2b rounds, applied to the previous block and to a reference block. Reference indices are data-independent in the first half of the first pass and data-dependent afterwards. The circuit implements the full algorithm, including the initial hash H0, the variable-length hash H′ and the final tag. It agrees with RustCrypto on 64 parameter cases.

bcrypt 2b

Based on the Blowfish key schedule. EksBlowfish initializes the 18-word P-array and four 256-word S-boxes from the hexadecimal digits of π. It mixes in the salt and password with 𝖤𝗑𝗉𝖺𝗇𝖽𝖪𝖾𝗒(𝗌𝗍𝖺𝗍𝖾,s,w), then performs 2cost iterations of

𝗌𝗍𝖺𝗍𝖾←𝖤𝗑𝗉𝖺𝗇𝖽𝖪𝖾𝗒(𝗌𝗍𝖺𝗍𝖾,0,w),𝗌𝗍𝖺𝗍𝖾←𝖤𝗑𝗉𝖺𝗇𝖽𝖪𝖾𝗒(𝗌𝗍𝖺𝗍𝖾,0,s),

and finally encrypts the string OrpheanBeholderScryDoubt 64 times. The 1,042 table words are supplied as advice, range-checked and matched against an in-circuit commitment to the standard constants.

MiMC-7 (test function)

An arithmetization-oriented function used to exercise the protocol at low cost. The password and salt are first absorbed with Poseidon2 into x0∈𝔽p, then 220 rounds are applied:

xr+1=(xr+cr)7,r=0,…,219,

with fixed round constants cr. Since gcd⁡(7,p−1)=1, the map u↦u7 is a permutation of 𝔽p, and each round is a single degree-7 constraint. MiMC-7 is not memory-hard, so it gives no meaningful resistance to password guessing; it serves only as a test vehicle.

9. Prover cost model

The prover materializes T, its β-fold extension, the composition polynomial and the Merkle trees, so peak memory is linear in the padded trace length:

M(L)≈c⋅2⌈log⁡2L⌉.

The MiMC-7 measurement (L=430,204, N=219, peak 4.25 GiB) gives c≈8.5 KiB per row. For Argon2id the cycle count scales with the work m⋅t. The measured L=19,593,971 at m=8, t=1 corresponds to roughly κ≈2.4×106 cycles per KiB-pass, so

MArgon2id(m,t)≈c⋅2⌈log⁡2(κ m t)⌉.

The model is first order: it ignores fixed overheads and assumes c is the same for every program. It does agree with the Argon2id run on a 125.6 GiB workstation, which committed 218 GiB before stalling on disk paging (see Experiments). Memory scales with the hash's work factor, and the work factor is precisely what makes the hash resist guessing, so general-purpose STARK provers are poorly matched to password hashing. The Future work page discusses ways around this.
