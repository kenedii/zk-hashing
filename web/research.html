Future work and references

Future work

Directions ordered from most to least immediate.

  • Segmented proving

    The inter-round state is small: 1,042 words for bcrypt and m KiB for Argon2id. Partition the execution into segments σ1,…,σk and prove, for each i, that σi maps a state with commitment Di−1=𝖯𝟤(𝗌𝗍i−1 ∥ ρ) to one with commitment Di=𝖯𝟤(𝗌𝗍i ∥ ρ). The verifier checks all k proofs and the chain D0→Dk. Each segment can be proved independently and in parallel, at about 13 GiB per 222-row segment. The per-login blinding value ρ is essential. Without it, an unblinded intermediate commitment would let an attacker test password guesses after computing only part of the hash. Recursive verification could later aggregate the k proofs into one.

    Designed

  • Zero-knowledge and higher security levels

    Adopt trace randomization, giving perfect zero knowledge, once the Miden prover supports it, and raise the conjectured security level above 96 bits to leave margin against quantum search.

    Depends on Miden

  • Memory64 browser proving

    MiMC-7 proving needs 4.25 GiB, just above the wasm32 ceiling. A wasm64 build raises the JavaScript API limit to 16 GiB (Chrome 133 and later, Firefox 134 and later) and should permit the first in-browser proof. Memory64 has been measured at 10–100% slower in other workloads; multi-threading through Web Workers may offset part of that.

    Next step

  • A prover specialized for password hashes

    In a general-purpose VM, each 64-bit operation costs several cycles of limb arithmetic and range checks. A dedicated AIR for the Blake2b/BlaMka or Blowfish round functions could cut the trace length L by orders of magnitude. A streaming prover that keeps the trace out of core would instead reduce the constant c in M(L)≈c⋅2⌈log⁡2L⌉. Together, these are the main open problem between the prototype and a practical login.

    Open problem
