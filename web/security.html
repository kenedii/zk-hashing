Security analysis

The guarantees the construction provides, the assumptions they rest on, how it compares with the standardized alternative, and the limitations of the current implementation.

Threat model

We consider four adversaries, in increasing strength:

  1. Network adversary. Observes and modifies traffic between client and server, but cannot read TLS-protected content.
  2. Transcript adversary. Obtains complete login transcripts (n,π), for example from a TLS-terminating intermediary, application logs or a compromised server.
  3. Database adversary. Obtains the stored records (C,s,θ).
  4. Quantum adversary. Any of the above, additionally able to run Shor's and Grover's algorithms at cryptographic scale.

The design goal is that no adversary short of the database adversary can authenticate as a user or recover the password at a cost below exhaustive guessing against Hθ, and that the database adversary gains nothing beyond what a conventional salted password-hash table already provides.

What an accepted proof establishes

Fix the pinned program hash hP and the server's records (C,s,θ). If 𝖵𝖾𝗋𝗂𝖿𝗒(hP,(C,s,θ,n),π)=1 for a fresh challenge n, knowledge soundness implies that, except with probability at most the knowledge error κ≈2−96, the prover knew some w satisfying

𝖯𝟤(τalg ∥ Hθ(w,s) ∥ s ∥ θ)=C.

By the binding property of the commitment, any such w is the registered password or a second preimage of Hθ. The circuit range-checks every password and salt byte, constrains the length to 1≤∣w∣≤64, and uses domain tags with explicit lengths, which excludes cross-algorithm and concatenation ambiguities. Because n is absorbed into the Fiat–Shamir transcript and marked as spent after use, a proof authenticates exactly one login.

Offline guessing

Let 𝒲 be the attacker's candidate list, ordered by estimated likelihood, and let cost(Hθ) denote the cost of one hash evaluation. Any party holding C can test candidates by recomputing the commitment, and succeeds after expected work

𝔼[work]≈cost(Hθ)⋅∑i≥1i⋅Pr⁡[w=wi].

This is the same bound as for a conventional salted hash. The salt prevents precomputation across users, and θ sets the per-guess cost. Two properties of the current implementation widen the set of parties who hold C:

  • C is a public input of every proof, so the transcript adversary learns it as well as the database adversary.
  • The proofs are not zero-knowledge. The committed trace polynomials are deterministic in w, so a proof is itself a guessing oracle. Testing a candidate this way costs at least one in-VM execution of Hθ, which is more expensive than testing against C directly, so this adds no new capability beyond what C already gives.

Proofs and commitments should therefore be handled as credential material: kept out of logs, and transported only over TLS.

Comparison with OPAQUE

OPAQUE (RFC 9807) is an asymmetric password-authenticated key exchange (aPAKE). The client blinds its password and obtains, through an oblivious pseudorandom function (OPRF) evaluated jointly with the server, a value rwd=Fk(w). Here k is a per-user key held by the server, and the server learns neither w nor rwd. In the prime-order-group instantiation, the client sends B=ℋG(w)r for a random r, the server returns Z=Bk, and the client unblinds Z1/r=ℋG(w)k. The value rwd then decrypts an envelope holding the client's long-term key, which is used in an authenticated key exchange.

Post-quantum considerations

OPAQUE. Shor's algorithm computes discrete logarithms in polynomial time. An adversary who observes one OPRF exchange (B,Z=Bk) can therefore recover k, then evaluate Fk(w′) for candidate passwords and test each against the envelope. This removes the protection against offline guessing that distinguishes an aPAKE. The session keys of recorded exchanges are likewise exposed to harvest-now-decrypt-later attacks, as the IETF hybrid PQ-PAKE draft notes. Post-quantum aPAKE designs, including the hybrid CPaceOQUAKE+ proposal and KEM-based compilers, are under development but not yet standardized.

STARK-based authentication. The argument uses only a hash function, through Merkle commitments and Fiat–Shamir, so Shor's algorithm does not apply. Generic quantum search still matters. Grover's algorithm finds a preimage in a space of size 2λ with O(2λ/2) queries. For the BCS construction underlying STARKs, Chiesa, Manohar and Spooner prove security in the quantum random-oracle model, with an adversary's success probability growing roughly quadratically in its number of oracle queries rather than linearly. A conjectured classical level of 96 bits therefore corresponds to a substantially smaller post-quantum margin, and a post-quantum deployment should use a higher security level.

Transport. The construction authenticates the client but establishes no key, so confidentiality and server authentication rest on TLS. A post-quantum deployment also requires post-quantum key agreement in TLS, such as the hybrid X25519MLKEM768 group now offered by major browsers. The password-flow baseline uses secp256k1 Schnorr signatures and offers no post-quantum security.

Limitations

  • Proving cost. At realistic parameters, Argon2id and bcrypt proofs need memory several orders of magnitude beyond client hardware when a general-purpose prover is used (cost model). The demonstrated settings, m=8 KiB for Argon2id and cost 4 for bcrypt, are far below recommended password-storage parameters.
  • No zero knowledge. The prover does not randomize the trace. Miden's roadmap lists perfect zero knowledge as future work.
  • Public commitment. As shown above, C is visible to any party that sees a proof.
  • No key agreement. The protocol provides one-way authentication and depends on TLS for everything else.
  • Side channels. Argon2id uses data-dependent memory addressing, and VM execution is not constant-time. Timing and resource side channels have not been analysed.
  • Scope. Passwords are 1–64 bytes, salts exactly 16 bytes, and Argon2id lanes 1–4. The Argon2id secret and associated-data inputs are not supported.
  • Assurance. Miden VM and the Rust-to-Miden compiler are experimental, and this code has not been independently audited. For deployments today, OPAQUE is the appropriate choice.

zk-hashing is a research prototype. It has not been audited and must not protect real accounts.
