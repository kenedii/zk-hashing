Proving a password hash runs into a memory wall

I compiled complete Argon2id, bcrypt and MiMC-7 into a STARK-provable virtual machine. All three run start to finish inside the circuit. Only MiMC could be proved on a 128 GiB workstation. This chart shows how far the other two fall short.

What runs inside the circuit

Each program takes the password as private input and the stored credential and a one-time challenge as public input. It recomputes the full hash inside the VM, then checks it against the credential. The verifier only accepts the exact compiled program, so a proof can't swap in a cheaper computation.

    Why the browser stops at 4 GiB

    The prover writes out the whole execution trace and its low-degree extension before it commits to anything. That costs roughly 3.2 KB per row, and the row count rounds up to the next power of two. A 32-bit WebAssembly page can address at most 4 GiB. Even MiMC, at 219 rows, stalled at that limit in Chromium, so proving happens in a native program and the browser only verifies.

    Argon2id and bcrypt are slow on purpose. Argon2id fills memory and bcrypt repeats its key schedule, so that guessing passwords is expensive. A general-purpose prover pays that cost again for every step it records. Turning the proof-security dial down doesn't help, because the trace itself is what's too big.

    Showing Argon2id and bcrypt without a supercomputer

    The full executions already pass natively. To put real proofs in front of people, these are the realistic routes:

    • Prove once on a big machine, verify anywhere

      Rent a cloud machine with 256 GiB or more for one run of the Argon2id proof, then publish the proof file. Verifying it here takes milliseconds on a phone. bcrypt cost 4 would need a machine with roughly 2 TiB.

      Planned

    • Prove one piece live in the browser

      Small circuits for a single Blowfish encryption or a single Blake2b compression should fit under the browser's limit. That would show the exact building blocks of bcrypt and Argon2id being proved in front of the visitor.

      Needs measuring

    • A prover built for these hashes

      A purpose-built constraint system, or a prover that streams its trace to disk, could cut memory by orders of magnitude. This is the open research question the numbers above point to.

      Open question

    What this isn't

    This is a measurement of cost, not a login system. If you want logins where the server never sees the password, use OPAQUE (RFC 9807). It does that in milliseconds with standard Argon2id settings.

    • The Miden VM is alpha software, and none of this code has had an independent audit.
    • The proofs use Miden's 96-bit security level.
    • It hasn't been confirmed that these proofs hide every detail of the password. Treat them as proofs of correct computation, not as proven zero-knowledge.
    • bcrypt cost 4 and Argon2id at 8 KiB are far below what you'd use to store real passwords.
