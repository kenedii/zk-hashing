What is this?

A short explanation for readers without a cryptography background: the problem this project addresses, the idea behind the solution, and what it does and does not achieve.

The problem

When you sign in to a website, your browser sends your password to the website's server. The connection is encrypted with HTTPS, so other people on the network cannot read it. The server itself, however, receives the password in readable form. It then hashes the password and compares the result with the value it stored when you registered.

That moment of exposure matters for several reasons:

  • Server compromise. An attacker who controls the server, even briefly, can record every password as users sign in. Stealing the stored hashes only allows slow guessing; observing live logins reveals passwords directly.
  • Accidental logging. Large services have disclosed incidents in which passwords were written to internal logs in readable form by mistake.
  • Intermediaries. HTTPS is often terminated before the request reaches the application, at a load balancer, content delivery network or corporate inspection proxy. Each of these sees the password.
  • Password reuse. Many people use the same password on several sites, so a password exposed at one service puts accounts elsewhere at risk.

Encryption protects the password on the way to the server. It does nothing once the password arrives. The question this project asks is whether the server needs to receive it at all.

The idea: prove you know it, without revealing it

A zero-knowledge proof lets one party (the prover) convince another (the verifier) that a statement is true without revealing why it is true. Here the statement is:

"I know a password which, when hashed with the salt and settings you stored for me, produces the value you registered."

Your browser performs the full password hash itself and produces a short proof of that statement. The server checks the proof. If the check passes, the server is convinced that you know the password, yet it never received the password or anything it could reuse to sign in as you.

A toy example: the cave with a locked door

This classic illustration, due to Quisquater and colleagues, captures the essential mechanism. A ring-shaped cave has one entrance, which splits into a left and a right passage. Deep inside, the two passages are joined by a door that opens only with a secret code.

The prover claims to know the code. To test the claim without learning the code, the verifier waits outside while the prover walks into one passage, chosen at random and out of sight. The verifier then calls out which passage the prover must come back through. A prover who knows the code can always comply, passing through the door if necessary. A prover who does not know it can only comply if they happened to choose that passage, which happens half the time.

    What the example shows

    • Soundness. A prover without the code is caught with probability ½ in each round. After $n$ rounds the probability of escaping detection is $2^{-n}$: below one in a million after 20 rounds.
    • Completeness. A prover who knows the code passes every round.
    • Zero knowledge. The verifier learns nothing about the code itself. A recording of the rounds would not even convince a third party, because the prover and verifier could have agreed on the called passages in advance. Formally, anything the verifier sees could have been produced without the secret; this is what "zero knowledge" means.

    Advantages and drawbacks

    What the approach offers

    • The server never receives the password, or any value it could replay to sign in as the user.
    • The server can confirm that the client ran the exact registered hash function with the registered settings, because the proof is tied to one specific program.
    • Anyone holding the public values can check a proof; no secret key is needed to verify.
    • The proofs rely only on hash functions, so there is no known way for a future quantum computer to forge them. Several current password protocols rely on mathematics that a large quantum computer could break.

    What it costs, and what it does not solve

    • Producing a proof for a real password hash is currently far too expensive for a phone or laptop: hundreds of gigabytes of memory for the smallest Argon2id setting.
    • The proof system used does not yet hide every detail of the computation, so proofs must be treated as sensitive.
    • If the server's database is stolen, attackers can still guess passwords offline, exactly as with today's password hashes.
    • It does not replace HTTPS, and it does not by itself authenticate the server to the user.
    • It is unaudited research software.

    Where the project stands

    The complete Argon2id and bcrypt algorithms run correctly inside the proving virtual machine, and a small test function (MiMC-7) has been proved and verified, including in the browser. Proofs of the real password hashes have not yet been produced, because general-purpose proving systems need memory proportional to the length of the computation, and password hashes are deliberately long computations. The Results page has the measurements.

    For password login without transmitting the password today, the established choice is OPAQUE (RFC 9807), a standardized protocol that is fast and well analysed. The Security analysis compares the two approaches.
